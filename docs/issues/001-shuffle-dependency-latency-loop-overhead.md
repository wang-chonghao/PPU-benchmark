# 核查 SHFL 依赖链的循环开销，确定有效结果延迟

状态：待核查、待补测。现有约 34 周期是内网测试摘要中的每步有效时间，尚不是已确认的纯 SHFL 结果延迟。本 Issue 不修改 GTSim 参数，不要求原始实测数据、PASM 或设备信息外传。

## 问题与目标

当前 `calibration_probe.cu` 的 `shuffle_chain` 每轮执行一条依赖 SHFL，同时执行循环计数、判断和跳转。按 steps 拟合运行时间可以排除固定的启动、初始化和输出开销，但循环控制也随 steps 增长，仍可能包含在斜率中。`r²=1.0` 不能证明每步时间全部来自 SHFL。

目标是在保留单 warp、单条串行依赖链的前提下，测出循环展开后的稳定有效间隔，判断约 34 周期能否作为 GTSim 的 SHFL 延迟近似。无需还原硬件内部所有流水级，也不能把本测试改成独立链吞吐测试。

参考源码：[shuffle 与计时入口](../../calibration_probe.cu)、[计时助手](../../probe_common.cuh)、[分析器](../../supplement.py)、[内网校准手册](../INTRANET_CALIBRATION.md)。

## 1. 核查现有 PASM

先确认内网源码版本与实际编译参数，再找到 `shuffle_chain` 的循环，记录：

- 每次机器循环执行的 SHFL 数，以及源指令实际对应的 PASM 序列。
- 下一条 SHFL 的输入是否确实依赖上一条输出；有额外寄存器移动、转换、同步或访存时逐项记录。
- 计数器更新、比较、分支和实际展开程度；不要假定源码循环与机器循环一一对应。
- 是否有删除、替换、spill、意外多链等情况。
- 是否为 1 block、32 threads；记录实际核心频率、SDK/编译器版本、寄存器使用及计时条件。

XOR shuffle 连续两次会恢复原来的 lane 排列。偶数次测试输出可能与初始值相同，因此正确性校验通过不等于目标指令全部保留。需同时核对 PASM，条件允许时核对动态指令数及其 per-thread/per-warp 计数口径。

## 2. 增加串行展开版本

新增 U=1、4、16、64 四个编译期版本，每次外层循环执行 U 条首尾相接的 SHFL。下面是沿用现有兼容指令的参考实现，仍需内网 SDK 编译验证：

```cpp
template<int U>
__global__ void shuffle_chain_unrolled(unsigned* out, int groups) {
    unsigned x = threadIdx.x;
    #pragma unroll 1
    for (int g = 0; g < groups; ++g) {
        #pragma unroll
        for (int j = 0; j < U; ++j) {
            asm volatile(
                "shfl.sync.bfly.b32 %0,%1,1,31,-1;"
                : "=r"(x) : "r"(x));
        }
    }
    out[threadIdx.x] = x;
}
```

`#pragma unroll` 不能代替 PASM 核查。确认内部循环确实展开，且每条 SHFL 依赖上一条；不能使用 U 个独立变量来替代这条链。保留输出校验，并用奇数/偶数总次数的额外正确性用例检查置换；这些用例不混入下面的整除计时矩阵。

## 3. 固定总 SHFL 次数进行计时

N 表示每个 lane 的总 SHFL 次数，同时也是完整 warp 的动态 SHFL 指令次数，后者须以实际 lowering 核对。主机传入 `groups=N/U`；不要给所有 U 传相同 groups 后继续声称工作量相同。

| 总次数 N | U=1 的 groups | U=4 | U=16 | U=64 |
| ---: | ---: | ---: | ---: | ---: |
| 256 | 256 | 64 | 16 | 4 |
| 1024 | 1024 | 256 | 64 | 16 |
| 4096 | 4096 | 1024 | 256 | 64 |

所有版本保持 1 block、32 threads，使用相同的输出处理、预热和计时方法。保留多个原始样本、实际频率和样本分散程度。只在短时计时精度不足时统一增加 N，并保持各版本使用相同的总次数集合。

当前 `elapsed` 已返回每次 launch 的平均时间，不要再次除以其内部重复 launch 次数。依赖间隔不除以 32 个 lane，也不把 cycles/step 再除一次已经计入 N 的 U。

## 4. 拟合与判定

每个 U 单独拟合，运行时间单位为微秒：

```text
T_U(N) = a_U + b_U * N
C(U) = b_U * 实际核心频率MHz
```

C(U) 为每条串行 SHFL 的有效周期数。频率明显变化的样本不能仅靠一个名义频率换算，应先分组或在稳定条件下复测。

| 结果 | 解释与下一步 |
| --- | --- |
| U=1/4/16/64 均接近 34 | 循环控制未显著抬高结果，支持约 34 周期的有效 SHFL 依赖延迟近似 |
| 随 U 增加下降，随后稳定 | 原始结果包含循环开销；保留稳定平台作为候选值 |
| U=64 时仍持续下降 | 尚未取得稳定平台，继续检查编译与计时，不立即定参 |
| 变化不规则或大 U 明显变慢 | 检查频率、寄存器压力、spill、代码大小和指令排布等变化 |

可辅助观察 `C(U) ≈ L_effective + H_loop/U`，但不要强制套用该形式。循环控制与 SHFL 可能重叠，不能按控制指令数量简单相加再相减，也不以空循环耗时相减作为主要证据。

稳定性应结合重复样本判断：例如 U=16 与 U=64 的差异不超过约 5%，且样本波动和拟合误差足以支持该判断，才认为已基本稳定；阈值仅为实验验收约定，不是硬件定律。较高 r² 仍不能代替指令保留、依赖和计数核对。

## 5. 与 GTSim 参数衔接

先登记有效依赖间隔，再检查模型的端到端链间隔。当前一组 32 lane 的 SHFL 服务时间为 1 周期、tail=4，即结果延迟 5 周期；调度唤醒还可能增加消费者的实际发射间隔。

若最终选择将有效 SHFL 结果延迟近似为 34 周期，在服务时间仍为 1 周期的条件下对应 tail=33，而不是 tail=34。这个换算仅是参数语义说明；最终还需把模型额外的依赖唤醒计时与实测链口径核对，不能重复添加。SHFL→SHFL 的结果不自动证明所有 SHFL→VALU 消费路径具有完全相同延迟，作为统一有效延迟使用时标明近似。
